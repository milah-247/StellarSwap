# Contributing to StellarSwap

Thanks for taking a look. This is a from-scratch constant-product AMM for
Soroban — see [`README.md`](README.md) for the math and architecture
before diving into the code; it explains *why* things are shaped the way
they are (the effects-before-interactions ordering, the reentrancy guard,
the minimum-liquidity lock) so changes don't accidentally undo a security
property.

## Workflow

1. Fork and branch off `main`.
2. `cargo test` must stay green — add new tests alongside any behavior
   change (see [`src/test.rs`](src/test.rs) for the existing style: one
   `setup()` helper, one focused assertion per test name).
3. `cargo build --target wasm32v1-none --release` must still produce a
   valid contract Wasm.
4. `cargo clippy --all-targets` should be clean, or any new warning
   justified in the PR description.
5. Open a PR describing *why*, not just *what* — especially for anything
   touching `math.rs`, `storage.rs`'s reentrancy lock, or the
   effects-before-interactions ordering in `lib.rs`.

## Good first issues

These are scoped to be self-contained — each touches one or two files and
comes with an obvious place to add tests.

### 1. Add a protocol fee switch

Right now all 30 bps of swap fee accrues to LPs (see the README's
[fee model](README.md#the-fee-model) section) — there's no cut for a
protocol treasury. Uniswap V2 added exactly this as an optional 1/6th
split of the fee, minted as extra LP shares to a configurable address
rather than transferred out of the reserves directly (so it doesn't
disturb the constant-product curve mid-swap).

**What to do:**
- Add a `protocol_fee_to: Option<Address>` admin-settable field in
  storage, plus an `set_fee_recipient(admin, to)` entry point gated by an
  admin address set at `initialize` time (you'll need to add an `admin`
  parameter to `initialize`, or a separate `set_admin`/two-step-ownership
  flow — either is fine, just document the choice).
- On `add_liquidity`/`remove_liquidity`, before minting/burning against
  the *current* `total_shares`, compute the growth in `sqrt(k)` since the
  last liquidity event and mint the protocol's cut of shares
  proportionally (this is the "mint on the sqrt(k) growth" trick Uniswap
  V2 uses — it means the fee is realized lazily, only when liquidity
  actually changes, instead of needing bookkeeping on every swap).
- Test: two LPs each with fee-switch on vs. off should not receive the
  same withdrawal amount for the same swap volume; the delta should match
  the configured protocol share.

**Where to look:** `math.rs` (you'll want another `checked_*` helper or
two), `storage.rs` (new `DataKey` variants), `lib.rs`'s
`add_liquidity`/`remove_liquidity`.

### 2. Multi-hop routing

Each pool only knows its own two tokens — swapping `X -> Z` when only
`X/Y` and `Y/Z` pools exist currently means two separate client-side
calls, with no atomicity between them (the first swap could land at a bad
price with nothing stopping it, since the second swap's slippage
protection can't see the first swap's actual output ahead of time).

**What to do:**
- Add a small router contract (new crate, e.g. `router/`, depending on
  this crate only for the `ConstantProductPoolClient` type) with a
  `swap_exact_in_multi(from, path: Vec<Address>, pool_ids: Vec<Address>,
  amount_in, min_amount_out, to)` entry point that calls
  `swap_exact_in` on each pool in sequence, feeding each swap's output as
  the next swap's input, entirely within one transaction.
- The *only* slippage check needed is on the final output vs.
  `min_amount_out` — intermediate hops can use `min_amount_out: 0` since
  the whole chain either completes atomically or the transaction (and
  every hop in it) reverts together.
- Test: a 2-hop `X -> Y -> Z` swap through two pools produces the same
  output as manually chaining `quote_amount_out` calls off-chain; a
  min-output set above what the full path can deliver reverts the whole
  chain (verify Y's mid-route balance is unaffected — nothing partially
  executes).

**Where to look:** this is mostly new code in a new contract, but reuse
`ConstantProductPoolClient` (generated by `#[contractimpl]` on this
crate) rather than reimplementing swap calls by hand.

### 3. Time-weighted average price (TWAP) oracle

`get_reserves()` only exposes the *instantaneous* spot price, which is
manipulable within a single atomic transaction/auth group — anything
using it for e.g. a lending protocol's collateral pricing needs a
harder-to-manipulate average instead.

**What to do:**
- Add two accumulator fields to storage — `price_a_cumulative` and
  `price_b_cumulative` (`i128`, or consider whether you need more
  headroom and should widen the type) — updated on every state-mutating
  call (swap, add/remove liquidity) as `accumulator +=
  current_price * time_elapsed_since_last_update`, using
  `env.ledger().timestamp()` for the clock. This mirrors Uniswap V2's
  `price0CumulativeLast`/`price1CumulativeLast`.
- Add a `price_cumulative() -> (i128, i128, u64)` view returning both
  accumulators and the timestamp they're as-of, so an off-chain (or
  another contract's) caller can snapshot it twice and compute
  `(cumulative_now - cumulative_then) / (time_now - time_then)` for the
  TWAP over that window themselves.
- Watch out for the overflow story here in particular — an accumulator
  that only ever grows needs either a type wide enough to not realistically
  overflow over the contract's lifetime, or an explicit wraparound
  convention (Uniswap V2 relies on `uint256` overflow wraparound being
  well-defined and differences still working out under modular
  arithmetic — decide deliberately whether you want that same trick with
  `i128`, or want to just panic and force a resize/migration past some
  threshold, and document the choice).
- Test: after N swaps with known amounts and controlled
  `env.ledger().set_timestamp(...)` calls between them (see
  `testutils::Ledger` in `soroban-sdk`), the computed TWAP over the whole
  window matches a hand-calculated expectation.

**Where to look:** `storage.rs` for the new fields, `lib.rs` for where to
hook the accumulator update into each mutating entry point.

## Reporting a security issue

If you find something that lets funds leave the pool without proper
authorization, breaks the `x*y=k` invariant, defeats the reentrancy guard,
or causes silent overflow, please don't open a public issue — see the
security contact conventions in the root of whichever repository hosts
this project, or reach the maintainers privately first.
